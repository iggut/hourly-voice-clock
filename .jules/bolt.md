## 2024-08-31 - [AudioTrack FloatArray Conversion Optimization]
**Learning:** In the local TTS synthesizer `AudioTrackPlayer`, native PCM samples were generated as a `FloatArray` but manually clamped and converted to a `ShortArray` via an iterative loop before being passed to `AudioTrack`. Because the app's `minSdkVersion` is 26, we can directly write the `FloatArray` to the `AudioTrack` by configuring it with `AudioFormat.ENCODING_PCM_FLOAT`, bypassing the CPU-heavy loop and intermediate array allocation.
**Action:** When streaming native `FloatArray` audio data in Android using `AudioTrack` (API 21+), always set `ENCODING_PCM_FLOAT` and write the `FloatArray` directly instead of manually clamping and coercing into `short[]`. Also, remember that `bufferSize` calculation needs to multiply by 4 (bytes per float) rather than 2 (bytes per short).
## 2024-11-20 - [Optimize String Parsing using substring]
**Learning:** In the TTS engine setup, the voice `inferGender` function was using `lower.split(Regex("[\\-_#\\s]"))` to separate name parts for gender lookup. Since `String.split` with regex creates a whole new list, it increases garbage collection and executes the regex engine repeatedly. Replacing this with an index-based tokenization loop and `substring()` allocates small specific chunks and bypasses the overhead for O(1) Map lookups, enhancing parsing speeds especially as the voice list grows.
**Action:** When extracting parts of a string inside loops, avoid using `split(Regex)` and instead use index-based loops to find delimiters, paired with `substring()` when matching extracted tokens to an O(1) Lookup structure.
## 2024-12-07 - [List Allocation Optimization]
**Learning:** In Jetpack Compose / Kotlin, using the `.map { }` extension function on a `Collection` to transform its elements creates a new `ArrayList` internally under the hood. While `.map { }` is often convenient, in high-frequency paths or for larger collections, explicitly pre-allocating an `ArrayList` to the exact target size and populating it with a simple `for` loop provides a more memory-efficient approach by eliminating intermediate collection copying overhead.
**Action:** When extracting and transforming elements from large lists or within frequent function calls, avoid `.map { }` chains in favor of a single-pass `for` loop that populates a pre-sized `ArrayList`.
## 2026-09-12 - [Avoid micro-optimizing idiomatic Kotlin collection functions]
**Learning:** Replacing idiomatic Kotlin `.map { }` and `.filter { }` with manually pre-allocated `ArrayList`s and `for` loops in an attempt to avoid intermediate list allocations is a meaningless micro-optimization. Because standard collection functions are `inline`, they already compile efficiently. Unrolling them sacrifices readability for zero measurable performance benefit.
**Action:** Do not manually unroll loops or avoid `.map`/`.filter` unless benchmarking proves a severe bottleneck in an extreme high-frequency path. If list transformations happen inside Jetpack Compose and cause allocation bottlenecks during recomposition, focus instead on wrapping the computation in a `remember` block so it executes less frequently.
## 2024-09-18 - [Voice Model Registry O(1) Lookups]
**Learning:** The `VoiceModelRegistry` singleton object previously resolved voice models by searching through a static list using O(N) `.find { }` and `.filter { }` commands. Because this list is queried frequently (e.g. on every screen composition in the settings screens and during TTS engine voice resolution), these linear scans generated unnecessary CPU cycles and list allocations (from `.filter`). Caching the static list using O(1) maps via `.associateBy { }` and `.groupBy { }` during object initialization improves lookup performance dramatically while preventing garbage collection pressure.
**Action:** When frequently querying static or immutable lists within Kotlin objects (singletons) by ID or category, replace repetitive O(N) `find` or `filter` calls with O(1) map lookups precomputed at initialization using `associateBy` and `groupBy`. This avoids redundant array allocations and list scanning.
## 2024-10-25 - [Jetpack Compose List Lookup Optimization]
**Learning:** Re-evaluating static or immutable lists using `.firstOrNull` (or similar array scanning methods) directly within Jetpack Compose recomposition paths (e.g., retrieving a model's display name or status based on an ID to compute a subtitle string) introduces unnecessary O(N) linear scans and garbage collection overhead that executes on every UI frame/state change.
**Action:** When pulling data from static or infrequently changing registries based on an ID within Jetpack Compose, use precomputed O(1) Lookup Maps (`VoiceModelRegistry.getVoiceById`) instead of linearly searching the original list (`VoiceModelRegistry.availableVoices.firstOrNull { it.id == selectedId }`).
